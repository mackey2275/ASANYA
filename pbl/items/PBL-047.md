# PBL-047 — Semantic Diffの外部AI分析用ファイル出力

- Type: Feature / Data / UX
- Status: Released
- Priority: Unspecified
- Released: v3.2.2
- Schema impact: None expected
- Persistence impact: None expected
- Migration: None expected
- Product Version: v3.2.2
- Last verified: 2026-10-25

## Objective

ASANYAの2時点スナップショット比較結果から、合意済みの分析指示と完全なSemantic Diffを一つに含む外部AI分析用ファイルを1回の操作で生成／downloadし、Microsoft 365 Copilot等へ最小限の手順で渡せるようにする。

想定する利用経路は次のとおり。

```text
ASANYA
→ compare two snapshots
→ one click
→ AI-analysis file is created/downloaded
→ attach/drag the file into Copilot
→ run analysis
```

## Confirmed scope and decisions

- 既存のSemantic Diff比較結果UIから、外部AI分析用ファイルを生成／downloadする明示的なactionを1つ提供する。
- 出力ファイルは、後掲のcanonical analysis instructionを先頭に、その時点の完全なSemantic Diffを続けて収録する。
- ユーザーが分析指示とSemantic Diff JSONを毎回手動でcopyし、ASANYA外で結合する必要をなくす。
- 現在のleading formatはMarkdownとする。任意の説明文をJSON objectの前へ置くとvalid JSONではなくなるため、説明文と完全なJSONを一つのhuman-readable fileとして扱える形式を採る。
- 代表構造は、`# ASANYA Semantic Diff Analysis`、canonical instruction、区切り、`# Semantic Diff`、JSON code blockの順とする。
- 代表filenameは `asanya_diff_2026-10-16_2026-10-23.md`。正確な日付／時刻表記はDevelopmentで確定してよい。
- Semantic Diffはlossy summaryへ変換しない。完全なSemantic Diffをsource dataとして含める。
- Compact Diff formatは本PBLへ含めない。
- Google ChromeとMicrosoft Edgeの両方で動作するordinary generated-file download／attachment経路を使用する。
- Human QAで失敗したvirtual-file dragおよびChromium固有`DownloadURL`を採用しない。新たな具体的証拠がない限り、direct-drag調査を本PBLで再開しない。
- raw clipboard transferはlarge Semantic DiffでCopilotのexecute／send actionが利用不能になり得るため、primary workflowとしない。
- likely implementationはmemory上に既に存在するSemantic Diffからのclient-side file generationだが、必要以上に実装方式を固定しない。

## Acceptance criteria

- Semantic Diff比較結果から1回のactionで外部AI分析用fileを生成／downloadできる。
- fileの先頭に本PBLで定義したcanonical analysis instructionが全文そのまま含まれる。
- instructionの後にcurrent complete Semantic Diffが欠落なく含まれる。
- fileはMicrosoft 365 Copilot等へ通常のfile upload／dragで渡せる。
- ChromeとEdgeの双方で生成、download、CopilotへのattachmentをHuman QAできる。
- ユーザーはinstructionやJSONを手動でcopy／結合する必要がない。
- large Semantic Diffをtext inputへ貼り付ける経路をprimary workflowにしない。
- Schema Version、persistence format、migration、保存済みSnapshot／Semantic Diffの意味を変更しない。
- 既存のSemantic Diff表示・copy・編集機能を不必要に退行させない。
- Product VersionはDevelopment／Release boundaryで決定する。

## Development-time questions intentionally left open

- exact button label: `AI分析用ファイルを保存`
- exact placement: 既存Semantic Diff comparison drawerのoutput actions内
- exact filename date format: `asanya_diff_<before YYYY-MM-DD>_<after YYYY-MM-DD>.md`
- raw JSON download: 追加しない。既存JSON表示／編集／copyを維持する
- canonical instruction representation: runtime JavaScript constantとしてPBL記録のcanonical textと完全一致させる

Developmentで次も確定した。

- export sourceは生成済みのauthoritative `snapshotComparisonState.semanticDiff`とし、AI／JSON textareaのuser edit bufferは使用しない。
- file bodyは `# ASANYA Semantic Diff Analysis`、canonical instruction、区切り、`# Semantic Diff`、complete Semantic Diff JSON code blockの順とする。
- UTF-8 Markdown Blob、temporary object URL、download anchorによるordinary generated-file downloadを使用する。
- 同一比較の反復downloadは同一内容／filenameを生成し、object URLは各回新規作成後に解放する。
- Schema 3.2、persistence format、migration、保存済みSnapshot／Semantic Diff semanticsは変更しない。

これらはDevelopmentで確定してよい。ただし、必須のuser-facing outcomeは次のとおり。

> One action generates a complete external-AI analysis file containing the canonical instruction plus the full Semantic Diff.

## Technical Probe evidence

- 元のuser goalは、Semantic Diffを会社承認済みMicrosoft 365 Copilotへ最小限の手順で渡すことだった。
- standalone diagnostic pageでdirect browser drag、Chromium `DownloadURL`、generated-file download、clipboardを調査した。
- ChromeとEdgeのHuman QA結果は実質的に同じだった。
- virtual `File` dragではCopilotにfile attachmentとして渡らず、raw JSON textがinputへ貼り付けられた。
- Chromium `DownloadURL`ではusable JSON fileではなく不明瞭なlink／stringが渡った。
- clipboardでもraw JSON textがinputへ貼り付けられた。
- 実際のlarge Semantic Diffではtext inputが長すぎてCopilotのexecute／send actionが利用不能になり得る。
- generated／downloaded local fileはChromeとEdgeの双方でCopilotへ正常にattach／dragできた。
- その後、毎回のprompt copyも不要にするため、合意済みASANYA analysis instructionをSemantic Diffの前へ自動収録する要求が追加された。
- proseとJSON objectの単純連結はraw JSONとしてinvalidになるため、Markdownをcurrent leading package formatとした。

## Canonical analysis instruction

次のtextはcurrent canonical analysis instructionであり、Development時も要約、言い換え、section削除を行わない。

```text
あなたは、タスク管理ツール「ASANYA」から出力された2時点間のSemantic Diffを分析します。

# 1. ASANYAについて

ASANYAは、Taskを以下のような情報とともに管理するタスク管理ツールです。

- Task title
- 親子階層
- Status
- Impact Level
- Due
- Summary
- Actual Start / Actual End
- Dependencies
- Recurrence
- その他Task管理情報

ASANYAでは、ある時点のTask状態をSnapshotとして保存できます。

2つのSnapshotを比較すると、ASANYAがTask単位のSemantic DiffをJSONで生成します。

このJSONは、単なるテキスト差分ではなく、

- Task追加
- Task削除
- 完了 / 再オープン
- Status変更
- Impact Level変更
- Due変更
- Summary変更
- Task階層の移動
- Dependencies変更
- Recurrence変更
- Actual Start / End変更

などを、Taskの意味上の変更として整理したものです。

今回あなたに渡すJSONは、このSemantic Diffです。

# 2. あなたの役割

変更項目を機械的に羅列するのではなく、

**「この期間に仕事全体がどう動いたのか」**

を、人が短時間で把握できるように整理してください。

特に、以下を区別して分析してください。

1. 完了
2. 新規流入
3. 優先度変更
4. 実質延期の可能性があるTask
5. 定例Taskの正常な次回ロール
6. その他、注意すべき変化

# 3. 最重要原則

## 3-1. 事実と解釈を分ける

JSONから直接確認できるものを「事実」としてください。

例：

- Impact Levelが2から3になった
- Dueが9/12から9/24になった
- 未完了のままDueが後ろへ移動した
- 新規追加された
- 期間内に完了した
- recurring TaskのDueとrecurrence base dateが同時に次回へ進んだ

一方、以下のような「理由」は、JSONに明示されていない限り断定しないでください。

- 優先順位が下がったから延期した
- 計画を見直した
- 他の仕事が忙しかった
- 課題定義ができていない
- 意図的に先送りした
- 作業が難航した

理由がJSONから判断できない場合は、

**「理由はSemantic Diffからは判断できない」**

と明示してください。

Humanが後から事情・原因・意図を補足する前提です。

## 3-2. due_changed = 遅延 と短絡しない

Due変更には意味の異なるものがあります。

少なくとも次を区別してください。

- 未完了のTaskの期限が後ろへ移動した
- 完了時に期限や実績日が調整された
- Recurring Taskが正常に次周期へロールした
- 新たに期限が設定された
- その他の期限変更

特にRecurring Taskについて、

- repeat / recurrence_rule がある
- dueが次周期へ進んでいる
- recurrence_schedule_dateも対応して進んでいる

場合は、原則として「延期」ではなく**定例ロール**として扱ってください。

ただしJSONだけで確定できない場合は、その旨を示してください。

## 3-3. added = 現在の負荷増加 と短絡しない

新規追加されたTaskの中には、

- 新規追加され、現在も未完了
- 新規追加され、同じ比較期間内に完了

の両方があります。

したがって、

「20件追加されたので20件分仕事が増えた」

とは解釈しないでください。

新規流入については、

- 新規追加総数
- そのうち期間内完了
- 比較終了時点で未完了として残っているもの

を可能であれば区別してください。

# 4. 分析観点

## A. 全体の流れ

可能であれば、

- Before時点の未完了Task数
- 新規流入数
- 期間中に完了したTask数
- After時点の未完了Task数

を整理してください。

データから計算可能であれば、

Before未完了
＋ 新規流入
－ 期間中完了
＝ After未完了

という形で、Backlog全体が増えたのか減ったのかを示してください。

無理に計算できない場合は推測しないでください。

## B. 完了

単純に完了Taskを全件列挙するのではなく、

- 同じProject / 親Task配下で複数Taskが完了している
- 親Task自体も完了している
- 一連の業務がまとまって収束した

といった「仕事の塊」があればまとめてください。

重要な単独Taskは個別に取り上げても構いません。

## C. 新規流入

特に、

- Impact Levelが高い新規Task
- Dueが近い新規Task
- After時点でも未完了の新規Task

を優先して取り上げてください。

期間内に追加・完了した短期Taskは、必要ならまとめて扱ってください。

## D. 優先度変更

Impact Level変更を確認してください。

特に、

- Impactが上昇した
- Impactが高い状態で未完了
- Impact上昇とDue後ろ倒しが同時に起きている

Taskは注意対象として示してください。

ただし、

「Impact上昇＋期限後ろ倒し = 正式に再計画した」

など、理由や意図までは推測しないでください。

事実として、

**「高Impactになった一方、未完了のまま期限も後ろへ動いている」**

までを示してください。

## E. 実質延期候補

次の条件を満たすTaskを確認してください。

- Beforeでも未完了
- Afterでも未完了
- Dueが後ろへ移動
- 定例ロールではない

これらは「実質延期候補」として示してください。

ただし、延期理由はSemantic Diffだけでは判断できないため、理由を創作しないでください。

特にImpact Level 2～3のTaskは優先して示してください。

## F. 定例ロール

Recurring Taskについて、通常の次周期への移行と判断できるものはまとめてください。

原則として個々を長々と列挙せず、

「週次・隔週等の定例Task ○件は正常に次周期へロール」

のようにまとめてください。

例外的・不自然な変化があれば個別に取り上げてください。

## G. その他の意味ある変更

以下も、仕事の意味が変化している場合は取り上げてください。

- Title変更
- Summaryの大幅変更
- 親子階層変更
- Dependencies変更
- Status変更
- Taskの目的やフェーズが変わったように見える変更

ただし、「なぜ変えたか」は推測しないでください。

# 5. 出力形式

以下の順序で簡潔にまとめてください。

## 1. 全体サマリー

3～6文程度で、

- 仕事量が増えたか減ったか
- 多く完了した領域
- 新しく入ってきた重要案件
- 高Impactで持ち越された案件

など、この期間の特徴を説明してください。

## 2. 完了した仕事

重要な仕事の塊を中心にまとめてください。

## 3. 新規流入

「新規追加後すでに完了」と「現在も残っている新規Task」を区別してください。

## 4. 優先度の変化

Impact Level変更を中心にまとめてください。

## 5. 実質延期候補

定例ロールを除外したうえで、

- Task
- Before Due
- After Due
- Impact Level
- JSONから確実に言えること

を示してください。

理由は推測しないでください。

## 6. 定例ロール

正常なRecurring Task更新を簡潔にまとめてください。

## 7. Humanに確認したい点

原因や意図が分からないもののうち、今後の判断に重要なものだけを質問候補として挙げてください。

例：

- 「このTaskは高Impactのまま期限が後ろへ移っています。理由はSemantic Diffから判断できません。単なる持越し、外部要因、作業内容未整理など、どのような事情でしょうか？」

質問を大量に作らず、重要なものに絞ってください。

# 6. 分析姿勢

目標は「変更点を漏れなく説明すること」ではありません。

目標は、

**多数のTask差分から、人が判断すべき重要な変化を圧縮して見せること**

です。

したがって、

- 重要でない変更はまとめる
- 同じ意味の変更はグループ化する
- 件数だけでなく仕事の塊を見る
- 高Impact × 未完了 × 期限後ろ倒し等のパターンを拾う
- JSONにない理由は推測しない
- 事実・分析・Humanへの確認事項を混同しない

ことを重視してください。
```
